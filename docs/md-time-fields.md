# CTP 行情的日期和时间字段

各交易所怎么填 `CThostFtdcDepthMarketDataField` 里的 `TradingDay`、`ActionDay`、
`UpdateTime`、`UpdateMillisec`，以及 `examples/watcher` 入库时怎么用它们。

依据标注：

- **[实测]**：在我们自己的 QuestDB 数据里查到的。11-02 夜盘来自旧表 `ctp_md_buffer`
  （存了原样的 `trading_day`、`action_day`、`update_time`；本机收到时间 2026-11-02
  22:58–23:02，周一夜盘），毫秒和夜盘交易所来自 `ctp_tick` 2026-11-03 全天（751 万行）。
  交易所按 `ctp_daily.exchange_id` 关联，行情前置本身不填 `ExchangeID`。
- **[公认]**：vn.py、ctpbee 等社区普遍记录的规则，我们还没有数据核对。

## 字段本意

| 字段 | 本意 | 格式 |
|---|---|---|
| `TradingDay` | 行情所属的交易日，夜盘算下一个交易日 | `YYYYMMDD` |
| `ActionDay` | 行情发生的自然日 | `YYYYMMDD` |
| `UpdateTime` | 交易所的最后修改时间，北京时间，不带日期 | `HH:MM:SS` |
| `UpdateMillisec` | 毫秒 | 0–999 |
| `ExchangeID` | 交易所 | 行情前置留空 [实测]，要从交易接口的合约查询拿 |

## 夜盘的实际填法

日盘各交易所 `TradingDay`、`ActionDay` 都是当天。问题都在夜盘。下面是 2026-11-02
（周一）夜盘、下一个交易日 2026-11-03 的实测值：

| 交易所 | `TradingDay` | `ActionDay` | 判断 | 依据 |
|---|---|---|---|---|
| 上期所 SHFE | `20261103` | `20261102` | 都对 | 实测，41,126 行 |
| 能源中心 INE | `20261103` | `20261102` | 都对 | 实测，7,873 行 |
| 大商所 DCE | `20261103` | `20261103` | **`ActionDay` 错**，填成了交易日 | 实测，14,165 行 |
| 郑商所 CZCE | `20261102` | `20261102` | **`TradingDay` 错**，填成了自然日 | 实测，9,854 行 |
| 中金所 CFFEX | — | — | 没有夜盘 | 实测：11-03 夜盘 `ctp_tick` 里没有它的行 |
| 广期所 GFEX | — | — | 没有夜盘 | 实测，同上；以后开夜盘要重新核对 |

还没核对的：

- **过零点**：上期所、能源中心夜盘开到 01:00 / 02:30，零点以后 `ActionDay` 应该变成
  次日 [公认]。旧表的数据在 23:02 就结束了，没有零点以后的样本。大商所、郑商所夜盘
  23:00 收盘，不过零点。
- **周五夜盘** [公认]：大商所 `ActionDay` 会填成下周一，差 3 天；郑商所 `TradingDay`
  填成周五。长假前最后一个交易日没有夜盘。

**结论：没有哪个日期字段能跨交易所通用。** `ActionDay` 大商所错，`TradingDay` 郑商所错。
按交易所分别修也可以，但要配交易日历，交易所以后改规则还得跟着改。

## 毫秒

`ctp_tick` 2026-11-03 全天，按交易所看 `ts` 的毫秒部分 [实测]：

| 交易所 | 毫秒取值 | 说明 |
|---|---|---|
| 上期所 SHFE | 0、500 各一半 | 每秒两笔快照 |
| 能源中心 INE | 0、500 各一半 | 同上 |
| 中金所 CFFEX | 300、800 各一半 | 每秒两笔，错开 300 ms |
| 大商所 DCE | 153 种，没有整秒 | 毫秒是真实的 |
| 郑商所 CZCE | **全是 0** | 只精确到秒，同一秒内的几笔 `ts` 相同 |
| 广期所 GFEX | 0–999 都有 | 毫秒是真实的 |

上期所和能源中心另有 19 行的毫秒是 45，都是订阅时补发的旧快照。

用郑商所的数据时要注意：同一合约同一秒可能有多行 `ts` 相同，按 `ts` 排序分不出先后，
要再按 `volume` 排。

## 其他和时间有关的坑

1. **订阅时补发旧快照** [实测]：2026-11-03 12:10 重启 watcher，收到了 870 笔前一晚
   20:59 的集合竞价快照；20:55 订阅时收到了 `UpdateTime` 为 18:43 等时间的快照。
2. **登录返回的 `TradingDay` 各所一致** [实测]：夜盘登录返回下一个交易日，
   2026-11-03 夜盘拿到 `20261104`。simnow-7x24 是回放环境，它的返回值不能当真。
3. **收盘后重复推送** [公认]：收盘后 `UpdateTime` 停在 15:00:00 附近继续推。
4. **集合竞价那一笔** [公认]：夜盘 20:59、日盘 08:59、中金所 09:29 各有一笔。
5. **`UpdateTime` 是唯一各所都填对的时间字段**，但它没有日期。

## watcher 的做法

| 列 | 来源 |
|---|---|
| `ctp_tick.ts` 的日期 | 本机时钟换算出的北京日期（`tick_rules.exchange_ts_us`） |
| `ctp_tick.ts` 的时分秒和毫秒 | `UpdateTime` + `UpdateMillisec` |
| `ctp_tick.trading_day` | 行情登录返回的 `TradingDay`，拿不到时才用 tick 里的 |
| `ctp_tick.insert_at` | db_writer 执行 flush 的本机时间 |
| `ctp_daily.ts` | 交易日当天北京时间零点 |

`ts` 的算法（`examples/watcher/tick_rules.lua`）：

1. 本机 epoch 加 8 小时，得到北京日期；
2. 拼上 `UpdateTime` 和毫秒；
3. **行情不会来自未来**：拼出来的时间比本机时间晚超过 `CLOCK_SKEW`（300 秒），就是
   前一天的；比本机时间早 24 小时减 300 秒以上，说明本机时钟慢、行情已经过了零点，
   算后一天；
4. 减 8 小时，转成 epoch 微秒写入。

几个例子：

| 本机时间 | `UpdateTime` | 得到的日期 | 情形 |
|---|---|---|---|
| 11-03 23:05:00 | 23:04:59 | 11-03 | 正常 |
| 11-03 00:00:01 | 23:59:59 | 11-02 | 跨零点，行情晚到 |
| 11-02 23:59:59 | 00:00:00 | 11-03 | 跨零点，本机时钟慢 |
| 11-03 12:10:00 | 20:59:00 | 11-02 | 重启时补发前一晚的快照 |
| 11-03 08:50:00 | 02:30:00 | 11-03 | 补发凌晨收盘的快照 |
| 11-03 09:00:00 | 09:05:00 | 11-03 | 本机时钟慢 5 分钟，还在容差内 |
| 11-03 09:00:00 | 09:05:01 | 11-02 | 超出容差，按前一天算 |

这套算法不依赖本机的时区设置，只要求本机时钟准，误差不超过 5 分钟。本机时钟比交易所
慢超过 5 分钟时，刚到的行情会被算成前一天，错整整 24 小时。部署的机器要开 NTP。

仍然算不准的情况：旧快照比本机时间早一天以上，比如周一早上收到周五夜盘的快照，日期会算成
周日。这些行 `insert_at - ts` 很大，下游用 `abs(datediff('s', ts, insert_at)) > 60` 排除即可。

2026-11-03 之前入库的数据用的是旧规则（相差超过半天才算跨零点），当天有 870 行补发的
前一晚快照被标成了当天晚上，`ts` 比 `insert_at` 还晚。同样可以用上面的条件排除。

## QuestDB 里的时区

QuestDB 存 epoch，网页控制台和 REST 接口都按 UTC 显示，库里的 `13:05:03Z` 就是北京时间
21:05:03。

- 按时间过滤用 UTC，或者带上时区；按交易日取数据直接用 `trading_day`。
- `SAMPLE BY 1d` 默认按 UTC 零点对齐。按北京自然日切要加
  `ALIGN TO CALENDAR TIME ZONE 'Asia/Shanghai'`；日 K 线按 `trading_day` 分组。
- 表按 UTC 的天分区，分区边界是北京时间 08:00，日盘、夜盘都不跨这个点。
- 只有 `entry.lua` 里 scheduler 的启停时间用本机时区（`os.date`），部署机器的时区
  要设成 `Asia/Shanghai`。
